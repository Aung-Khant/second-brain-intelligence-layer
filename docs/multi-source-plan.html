Implementation plan · codex/multi-source-capture

Beyond YouTube

Four new resource types — websites, articles, GitHub repositories, and research papers — added without disturbing the pipeline that already works. The order below is chosen so each phase ships something usable and the riskiest work happens once the shape is proven.

The shape of the change

One seam, four adapters

Everything downstream of capture is already source-agnostic. Both AI passes, the confidence bands, the taxonomy matching, the correction log, and duplicate detection care about a title, a description, and some text — not about YouTube.

The YouTube assumptions are concentrated in five places, and only these five need to change: the sourceType union, the validation gate, the extractor in the popup, the Notion Type map, and the nouns in the pass 1 prompt.

So the work is not four features. It is one refactor that turns capture into a registry of adapters, then four adapters written against that interface. Each adapter answers the same four questions: does this URL belong to me, how do I read this page, is what I read really this page, and what Notion Type is it.

The four types

What each one actually needs

They differ far more than the request implies. Two are nearly free, one is mostly prompt work, and one carries almost all the risk in this project.

GitHub repositories

Easiest

The only type with a real API. No scraping at all: the backend calls api.github.com/repos/{owner}/{repo} and gets a description, topic tags, primary language, and star count as clean structured data.

Detect
github.com/{owner}/{repo}, excluding reserved paths
Extract
Backend fetch. README as pageText if the description is thin.
Identity
Strong. The API echoes full_name; compare with the URL.
Risk
Rate limit of 60/hour unauthenticated. Fine for one person.

Research papers

Moderate

Academic publishers almost universally emit Highwire Press meta tags — citation_title, citation_author, citation_abstract, citation_doi. Where present, extraction is deterministic and excellent: the abstract is a better summary input than anything on a normal web page.

Detect
Host list (arXiv, DOI, PubMed, bioRxiv, ACM, IEEE, SSRN) plus a meta-tag probe
Extract
In-page meta tags; abstract becomes the description
Identity
DOI or arXiv ID, compared against the URL
Risk
PDF URLs have no DOM. Rewrite arXiv /pdf/ to /abs/.

Articles & blog posts

Hardest

The risk lives here. Classification quality depends on real body text, and getting clean body text out of an arbitrary page is a genuinely hard problem — the one part of this plan most likely to be underestimated.

Detect
Page signals, not URL: <article>, og:type, JSON-LD, a byline
Extract
Densest text container, nav/aside/footer stripped, capped
Identity
Weak. Canonical URL comparison only.
Risk
Paywalls, cookie walls, JS-rendered bodies, comment sections

General websites

Easy

Deliberately the fallback: anything that isn't one of the others. Tools, docs, product pages, landing pages. Expectations should be lower — title, description, and whatever text is there.

Detect
Any http/https page no other adapter claims
Extract
Shared with articles; same code, lower expectations
Identity
Canonical URL comparison
Risk
Low. Thin metadata yields a thin summary, which is honest.
Sequence

Four phases, each shippable

The refactor lands first with no behaviour change at all, so any regression it causes is visible immediately against the existing tests rather than tangled up with a new source type.

Phase 0

The seam — no new types, no behaviour change

Turn the YouTube-shaped path into a registry. All 64 tests must still pass untouched; that is the entire success criterion.

  • Widen sourceType, add shared/capture/source.ts
  • Split validation into shared checks plus a per-adapter identity check
  • Replace the popup's parseYouTubeTarget gate with detectSource
  • Parameterise the pass 1 nouns instead of hardcoding video/channel
Phase 1

GitHub repositories

Proves the seam against a genuinely different shape — data fetched by the backend rather than read from the page — while being the least risky of the four.

  • Backend fetch with a short timeout and a clear failure message
  • Topic tags map unusually well onto Notion Topics
  • Falls back to page extraction if the API is unreachable
Phase 2

Websites and articles

One extractor serving both, with the article/website decision made from page signals at capture time — a fact about the page, so code decides it, not the model.

  • Start with a compact heuristic extractor, roughly 60 lines
  • Keep it behind an interface so Readability can replace it later
  • Populate pageText, which has been null since day one
  • Cap extracted text before it reaches the prompt
Phase 3

Research papers

Last because it is the narrowest, and because by then the webpage adapter exists as a fallback for any publisher that doesn't emit citation tags.

  • Highwire citation_* tags, then JSON-LD, then the webpage fallback
  • arXiv PDF URLs rewritten to their abstract page
  • Authors become the creator; the abstract becomes the description
Blocked on you

Three decisions I should not make alone

Your Notion Type options don't cover this

The Type select currently offers Article, Video, YouTube Channel, Website, and PDF. GitHub repositories and research papers have nothing to map onto, and writing a value that doesn't exist is the same hard 400 that broke Save twice already.

Recommended: add Code Repository and Research Paper as options in Notion. The alternative — folding them into Website and PDF — costs you the ability to filter on them later.

How hard should article extraction try?

A compact heuristic extractor is quick and handles most blogs. Vendoring Mozilla's Readability handles far more of the long tail but adds roughly 100 KB to the extension and a dependency to keep current.

Recommended: heuristic first, behind an interface. Swap in Readability only if real use shows it is needed — and by then you will know which pages fail.

Identity checking gets weaker, and that is a real loss

For YouTube, capture is proven correct by comparing video IDs — that is what stops one video's metadata being saved under another's URL. A general web page has no such ID, so the strongest available check is comparing the canonical URL.

Recommended: accept the weaker check for web pages, and keep the strict one for every type that has a real ID — YouTube, GitHub, DOI, arXiv. Worth knowing rather than discovering later.

Known risks

What could go wrong

Body-text quality decides classification quality

Every downstream improvement rests on pass 1 receiving something worth reading. A page whose extraction yields navigation chrome produces a confident, useless summary — and the confidence bands will not catch it, because the model is not uncertain, just wrong.

The taxonomy still has no descriptions

Adding four source types multiplies the volume of things being classified against Areas and Topics that are bare names. This gets worse with scale, not better, and no amount of prompt work substitutes for one line of description per entity.

Pages behind a login or paywall

In-page extraction sees exactly what you see, which is the right call — but it means what gets saved depends on your session, and the same URL can capture differently for someone else.

Browser-rendered PDFs have no DOM

A PDF open in Chrome's viewer cannot be scraped at all. arXiv can be handled by rewriting to the abstract page; a bare PDF elsewhere will have to save as URL and title alone, and should say so rather than pretending.
